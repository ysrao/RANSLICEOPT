    RL Slice Optimizer MDP · PPO-clip · 64×64 MLP

    A policy/value network learns to adjust per-slice target shares online, rather than tuning the sliders above by hand. Formulated as an episodic MDP over the same PRB pool and capacity-guard floors used elsewhere on this page, trained in-browser with clipped-surrogate PPO and GAE advantage estimation.

    State (11-d): normalized PRB pool size, spectral efficiency, per-slice demand (3), per-slice current target share (3), per-slice minimum floor (3).
    Action (3-d, continuous, Gaussian policy): bounded per-step Δtarget for URLLC / eMBB / mIoT (±4 pts), clamped to each slice's [min,max] and renormalized against the 100% pool by reclaim priority.
    Reward: Σ wᵢ·min(1, targetᵢ⁄demandᵢ) − 0.5·(hard-floor violations, from the same guard above) − 0.1·(unallocated PRB waste) − 0.02·‖action‖².
    Networks: separate actor and critic, each a 64×64 MLP (2 hidden layers, tanh activations, He-scaled init); action std is a learned state-independent parameter per dimension.

    Fair-Optimal Solver not RL — water-filling

    A direct, non-learned answer to "what's the best balanced setting": weighted water-filling finds the target allocation that maximizes the worst-off slice's satisfaction ratio, subject to the same capacity-guard hard floors used above, each slice's own [min,max], and the 100% pool budget. Unlike PPO's scalarized reward — which can rationally decide to fully sacrifice the lowest-weighted slice — this explicitly optimizes for balance and reports when a slice's own Max slider, not pool scarcity, is what's capping it.

    Mean episodic return per training iteration (shaded band = ±1 std across the episode batch). Training and inference both run locally in this page — no data leaves the browser.

    Baseline Comparison

    Evaluates the trained PPO policy (deterministic) against four non-learning baselines on identical seeded demand trajectories — same starting targets, same random demand sequence per episode — so any gap is attributable to the policy, not to luck. Fair-optimal re-solves the water-filling allocation above every step against the live demand. Static is today's app behavior with no RL at all: targets held exactly as configured on the Slice Panel. Greedy is a simple reactive controller (moves target toward current demand, clamped to [min,max]). Random is a sanity floor.
